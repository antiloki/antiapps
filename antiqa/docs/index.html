01

Overview

antiQA (QA Anything) is an end-to-end tester for any app. It reads a pack that describes your product, plays your user stories in a real browser, a terminal or a window, crawls for what the stories missed, runs accessibility checks, and writes a bug report a coding agent can pick up.

It is one offline binary, antiqa, written in Rust. Verdicts are computed in code from what the screen showed. A model, when you choose to use one, only proposes stories, describes a screen or drafts a candidate; it never decides a verdict, and it always runs on this machine.

antiQA is alpha. The current download is 0.0.43, a Linux x86_64 build. Parts marked next release are built and tested on the development branch and are not in that download yet.

02

Install

Download the Linux build from the download section (or the binary directly), check it against SHA256SUMS, make it executable and put it on your PATH.

chmod +x antiqa-linux-x86_64 && mv antiqa-linux-x86_64 ~/.local/bin/antiqa
antiqa --version
antiqa doctor      # which tools this machine has: Chrome, ffmpeg, AT-SPI, a local model server

The AppImage is the window (antiqa-desktop). macOS and Windows builds were not made. planned

Build from source

rustup target add x86_64-unknown-linux-musl
cargo build --release --target x86_64-unknown-linux-musl

03

Quick start

  1. Start your app, for example on http://127.0.0.1:8080.
  2. Discover it and draft a pack, with stories written by code from what the scan found:
    antiqa onboard --scan --name myapp --url http://127.0.0.1:8080
  3. Run every stage against the running app:
    antiqa --product myapp --url http://127.0.0.1:8080
  4. Open reports/. Read BUG-REPORT.md, and hand evidence.zip to whoever fixes it. After a fix, replay just that story: antiqa --product myapp --url … --story <id>.

A desktop window: antiqa onboard --app "path/to/tauri-app" --name myapp (Tauri/WebKitGTK) or --native "gnome-calculator" (GTK, Qt, read over the accessibility bus). A command-line program: antiqa cli onboard "mytool" --name mytool. antiqa dashboard serves your local runs for the antiQA window.

04

Packs, stories and plays

A pack lives in packs/<product>/. It holds:

  • A manifest that names the product and where its parts are.
  • STUDY.md, a written study of the app. The study gate checks it has the required sections.
  • User stories and the coverage checklist.
  • Plays, the steps that act out each story, in the qaa.play/2 format.
  • A harness that starts or attaches to the app and checks its health.

When the app changes, antiqa drift says which stories went stale, antiqa heal mends what a rename broke and refuses the rest, and antiqa grow writes stories for what the app gained.

05

The six stages

Pick a stage with --stage. The default is all, which runs the six in order. Each stage is a gate: if it fails, the run stops with exit code 2.

StageWhat it does
studypacks/<product>/STUDY.md must have the required sections.
storiesChecks the story schema, the plays and the coverage checklist.
harnessStarts or attaches to the app, checks health, and refuses forbidden writes.
runPlays the stories, crawls the app and runs accessibility checks on each palette.
triageClassifies every miss.
reportWrites BUG-REPORT.md and evidence.zip.

Choosing how the app starts

FlagUse it when
--url <address>The app is already running. antiQA will not stop it.
--core <path> --fe <path>You have checkouts the pack knows how to start.
--stubUse the pack's harness stand-in. Good for testing the pack itself; never a verdict on the product.

07

Agents and MCP

An agent can use antiQA two ways. From a shell: antiqa --product myapp --url … --json 2>progress.log prints one JSON result on stdout (qaa.result/1: the exit code, the verdict, the failure count and the paths of the report files). Or over MCP: antiqa mcp is a stdio server whose tools list packs and stories, start a run, wait for it, read the report and re-run one story. Both read and write the same run folders as the window.

--agents stub is the default: every stage is deterministic and no model is used, which suits CI. --agents external writes agents/*.prompt.md plus the inputs into the report's handoff folder and stops if the expected artifact is missing.

08

Reports and exit codes

Reports go to reports/ (change it with --out). A failing story is played again to show how often it fails: 3 times for all, triage and report, once for a bare run. Change it with --repro. Only items triage calls a defect are product bugs.

ExitMeaning
0No product defect.
1At least one defect.
2A gate failed. This includes an unreachable app, a failure with no video, a report that says “always” without N of M, a shared evidence hash, or a missing binary stamp.

09

The window

antiqa dashboard serves a local runs server; antiqa-desktop is the window. It shows the same run folders the command line writes, so what an agent or a script does appears there. Across projects it has an Inbox of what needs you, Issues, Reports, and Health, which tests every project of a set with antiqa family. Per project it has Stories, Runs, Issues and Map.

next release The window gains Look, Quality, Knowledge (the error library) and Routines, and a Record page: antiqa record opens the app, you do the thing once, and every step is saved as a story as you go, shown live in the window.

Stories next release

One page for every story of the project. Switch between a List and Steps (each story's steps as a row of circles that pass, pulse or fail while a run plays), and group by result or by persona. The checkbox selects stories for Run selected, Persona… and Schedule…; clicking a story opens its side panel: its steps (with the error of a failed one), its schedule, and Run this story. Personas say who a story is for and are added in the sidebar.

Keys

Ctrl-K opens the command palette. C add a project, S scan, R run, N new story, X select, J/K move, G I Issues, G X Inbox, G H Health, G S Stories, G R Runs, Esc Esc stop everything.

10

Routines next release

A routine is a schedule on a story. On the Stories page select stories and choose Schedule… (or open one and use its Schedule section), then pick a preset (Every 30 minutes, Hourly, Daily, Weekdays, Weekly) or write a cron expression in local time. The dialog shows the schedule in words and its next three times. The Routines page is the one scheduler for all of them, with a Timeline of the day and a Board (Running, Waiting for a free slot, Scheduled, Needs attention, Paused).

CronMeans
0 2 * * *every day at 02:00
30 6 * * 1-5weekdays at 06:30
*/15 9-17 * * mon-frievery 15 minutes, 09:00 to 17:45, Monday to Friday
  • One at a time. Only one heavy job runs on the machine. Nothing starts while less than 2.5 GB of memory (or 1.5 GB of video memory, with an NVIDIA GPU) is free; the page says why it is holding back.
  • Together. Stories of one project that come due in the same minute start as one run, so the app opens once, and each routine still gets its own result.
  • Missed runs. Run once if due in the last 6 hours (the default), always run once, or skip. Skipped runs are written in the history with the reason. Each routine has a time limit that stops it. Pause all stops everything from starting.
  • Seen everywhere. A run started by a routine carries a chip in the project's Runs list, and a routine whose last run failed appears in your Inbox.
  • With the window closed. antiqa routines unit prints the two files of a systemd user timer (antiqa routines run-due every minute). antiQA prints them; you install them. A lease keeps the window and the timer from both acting.
  • Other actions. Besides a story: a health sweep, a look scan, growing the error library, syncing GitHub issues.
antiqa routines list      # name, state, schedule, next run, last result
antiqa routines run-due   # run what is due and wait for it
antiqa routines unit      # print the systemd timer files

11

Issues and the error library next release

An issue reads like a GitHub issue, and everything in it is written by code: what happened, the replay command, the environment, a marked picture (circles, boxes and arrows drawn by code over where pictures differ), and tabs for the failure, the video, the console and the network requests around it. Send it to GitHub, and keep it in step: a fixed bug closes its issue, one that came back reopens it. Per project, a run can do that for you (off by default; new issues at most five a run).

The error is fitted to a shape in a library of 439 (HTTP, network, JavaScript, security, loading, accessibility, terminal, frameworks, desktop, storage, auth, API, layout). The shape says what is common for that kind of error: common causes, each with how to confirm it, and common fixes. It is never a diagnosis of your program. The library grows: antiqa errors draft asks a local model for a candidate for a kind nothing describes, code writes the pattern and vets it against real examples, and you promote or reject it. antiqa errors export and import move your shapes between machines.

The local models are only an optional second look on an issue, shown apart and never filed.

12

Quality X-ray next release

Project › Quality counts the health of the product from the history of its runs. No source is read and no model takes part. It shows pass rate and its trend, a matrix of every story in every run, where each failing story last passed and first failed, issues that came back after a fix, how long fixes took, where issues pile up by screen and severity, the kinds of error that cause most issues, tests whose result flips back and forth, and a calendar of runs. Web projects also check the errors the page logs and the requests that fail, on every story.

13

Desktop programs next release

A program with a window runs out of sight on a display of its own, so it never takes over your screen. A program that keeps your data beside itself (a pendrive build) is run from a copy without that data, with a home folder of its own: sign in once in its own window and later runs start signed in. antiQA never asks for or keeps a password. A page's file picker is answered from the project's test-files folder instead of opening a native window nobody could see, so an upload replays the same way every time.

15

Troubleshooting

The run stops with exit 2

A gate failed. The output names it. Fix the pack (study sections, story schema) or the harness, then run again, using --reuse-* to skip stages that already passed. antiqa doctor shows what this machine is missing.

I only want to check one story

Use --story <id> --headed to watch it play.

16

FAQ

Does it need Node or Python?

No. It is a single Rust binary.

Does it send data anywhere?

Runs and reports stay on your machine. With --agents stub no model is used at all, and a local model, when you turn one on, runs on this machine. GitHub is used only when you connect it and send an issue.

Is there a desktop window?

Yes: antiqa-desktop, a Tauri window, in the AppImage. See The window.

Where are the full guides?

In the repository under docs/: the window, Routines, Quality, Issues, desktop programs and the window's local HTTP API.

Does a model decide whether my app passed?

No. The verdict, the issue text, the error shape and the quality numbers are computed by code.
